# 电动汽车充电平台测试计划

- **项目名称**：东软电动汽车充电桩应用管理平台
- **文档版本**：v1.0
- **编写日期**：2026-09-09
- **编写人**：质量保障组
- **适用环境**：Ubuntu 22.04、Qt 用户端/管理端、SQLite、Web 看板；自动化在 WSL 项目 `/home/ylinz/bitse-bydxxq` 执行

## 第一章 引言

### 1.1 编写目的

本计划指导本项目在实训周期内完成需求验证、异常验证、回归和交付验收，明确测试范围、策略、资源、进度和质量门禁。测试重点覆盖用户充电闭环、管理端风控、数据库一致性、预测服务和 Web 看板。

### 1.2 项目背景

系统由 Qt 用户端、Qt 管理端、Socket/HTTP 服务、SQLite 数据库、Python 负荷预测服务和 Web ECharts 看板组成。核心数据流为“登录/充值→站点检索→预约→充电→结算→订单/钱包/看板同步”。

### 1.3 术语和优先级

- **P0**：主链路或数据安全场景，发布/演示前必须通过。
- **P1**：重要功能和异常场景，允许在明确风险下延期。
- **P2**：体验、兼容性和低风险补充场景。
- **RTM**：需求追踪矩阵，用于关联需求 ID、测试用例和缺陷。
- **幂等**：同一请求重复提交只产生一次业务结果。

### 1.4 参考资料

数据库架构设计、数据库函数调用说明、项目分工划分、`测试用例补充对照表.md`、`TEST_CASE_LIST_TEMPLATE.xlsx`、项目 `README.md` 及接口契约文档。

## 第二章 测试必要性

### 2.1 业务价值

验证余额、订单和设备状态在正常及异常流程下保持一致，避免重复扣款、错误占桩和看板数据失真，保证演示主链路可重复执行。

### 2.2 质量门禁

发布或演示前：P0 用例通过率不低于 95%，不得存在未关闭 P0 缺陷；正常充电闭环、余额不足、重复提交、冻结风控、服务重启恢复和数据库事务回滚必须通过。当前自动化回归结果为 30 passed。

### 2.3 协作价值

所有用例使用统一编号和需求 ID，缺陷按模块、优先级、复现步骤、实际/预期结果和日志记录；每周同步 RTM 状态，跨端问题由质量保障组跟踪到回归关闭。

## 第三章 测试范围

### 3.1 纳入范围

- 用户登录、资料修改、头像校验、充值和钱包流水。
- 电站/电桩查询、价格展示、预约、取消和并发抢桩。
- 充电仿真、暂停/恢复、异常退出、订单结算、余额不足和重复结算。
- 管理员登录、站点/电桩运维、远程重启、故障切换、用户冻结/解冻。
- 统计看板、营收趋势、设备状态、用户增长和负荷预测回写。
- SQLite 约束、触发器、事务回滚、WAL 完整性和 outbox 事件。
- HTTP 请求校验、服务重启恢复、Web 看板接口降级和跨端联调。

### 3.2 不纳入或降级范围

真实支付渠道、真实地图配额、生产级多租户 RBAC、真实大规模压测和生产 OSS 计费不作为本次硬门禁；使用模拟服务或记录外部依赖限制。

## 第八章 资源与风险

| 风险 | 影响 | 应对 |
|---|---|---|
| Qt 客户端未运行或构建环境缺失 | UI 用例无法执行 | 先运行项目构建脚本；服务层自动化先行，现场补测 |
| 地图/远程服务配额或网络不可用 | 路线和远程调用失败 | 使用 mock，记录错误码并验证降级提示 |
| 数据库文件损坏或只读 | 写入和恢复受阻 | 复制测试目录，执行完整性检查，失败后恢复备份 |
| 服务强杀/断网造成状态悬挂 | 重复订单或脏数据 | 使用独立目录，核对订单、余额、流水和 outbox |
| 种子数据被重复加载 | 统计和余额失真 | 验证固定业务编号、唯一键和不重复播种 |

## 第九章 缺陷管理与报告

缺陷等级沿用 P0/P1/P2。缺陷必须包含环境、版本/提交号、前置数据、复现步骤、实际结果、预期结果、日志或截图、影响范围和回归结论。测试日报记录执行数、通过数、失败数、阻塞数和新增/关闭缺陷；最终报告附自动化日志、现场记录、RTM 和遗留风险。
